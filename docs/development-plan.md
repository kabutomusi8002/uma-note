# 開発手順

## 1. 前提と安全方針

- Next.js App RouterとTypeScriptを用い、スマートフォン優先で実装する。
- 永続データはSupabase PostgreSQLを正本とする。
- ブラウザから使用する公開キーはRow Level Security（RLS）と組み合わせ、利用者ごとにデータを分離する。
- service role keyはサーバー管理処理だけで使用し、クライアントコードやNEXT_PUBLIC_で始まる環境変数には置かない。
- 予想案と実購入券面は別テーブル／別レコードとして保持する。
- ロック時スナップショットと変更履歴は追記型にし、過去内容を破壊しない。
- 自動投票機能および投票サイトへの購入送信は実装しない。

## 2. Supabase接続準備

1. Supabaseでプロジェクトを作成する。
2. Project settings > APIからProject URLとanon key（またはpublishable key）を取得する。
3. .env.exampleを.env.localへコピーする。
4. NEXT_PUBLIC_SUPABASE_URLとNEXT_PUBLIC_SUPABASE_ANON_KEYを設定する。
5. マイグレーションを適用し、全ユーザーデータテーブルでRLSを有効化する。
6. 認証ユーザーIDを所有者列へ保存し、select、insert、update、deleteの各ポリシーを確認する。

SUPABASE_SERVICE_ROLE_KEYとDATABASE_URLは管理・マイグレーションで必要な場合だけ設定する。これらをフロントエンドへ含めない。

## 3. 実装フェーズ

### Phase 1: データ設計

- 開催・レース、出走馬、予想、印、予想買い目、実購入券面、結果、払戻、反省、変更履歴、ルール／ルールバージョンを定義する。
- 金額は浮動小数点ではなく円単位の整数で保持する。
- レースは開催日・競馬場・レース番号で一意にする。
- 予想ロック時刻、発走時刻、作成・更新時刻はタイムゾーン付きで保持する。
- 参照整合性、重複買い目防止、券種の許可値をDB制約でも守る。
- RLSと必要なインデックスをマイグレーションへ含める。

完了条件は、空のSupabaseプロジェクトへ同じスキーマを再現でき、別ユーザーのデータが読み書きできないこと。

### Phase 2: PWA・モバイル基盤

- マニフェスト、192px／512pxアイコン、テーマ色、standalone表示を設定する。
- Service Workerを本番環境だけで登録する。
- 公開アプリシェルと静的資産をCache Storageへ保存し、API／Supabase応答は保存しない。
- レースとルールの作業コピーは端末のlocalStorageへ自動保存し、オフライン再起動後も復元する。
- safe-area、44px以上のタップ領域、360px幅での横はみ出し防止を共通スタイルに反映する。

Service Workerを変更したらpublic/sw.jsのCACHE_VERSIONを更新し、古い静的キャッシュを削除する。

### Phase 3: 開催・予想入力

- 開催日、競馬場、レース番号、発走時刻の作成・編集を実装する。
- 印、選出馬、展開、馬場、危険人気、穴馬、買い／見送りを保存する。
- 未保存、保存中、保存済み、エラーを明示する。
- 発走時刻以降の予想変更をUIとDBの双方で拒否する。

### Phase 4: 買い目計算

- 3連複・3連単・馬連・ワイド・単勝の入力を実装する。
- 通常、ボックス、フォーメーションを具体的な組み合わせに展開する。
- 同一組み合わせを正規化して重複を除く。
- 点数、1点金額、小計、合計投資額を純粋関数で計算する。
- 予想案から実購入へコピーできるようにし、コピー後は独立して編集・保存する。

計算ロジックは境界値、順序違い、重複、0円、不正な馬番を含めて単体テストする。

### Phase 5: ロックと監査履歴

- ロック操作前に確認画面を表示する。
- ロック時に予想全体のスナップショット、ロック時刻、ルールバージョンを記録する。
- 更新ごとに変更前後または差分、変更者、変更理由を追記する。
- ロック済みデータの通常更新を禁止し、訂正は新しい監査記録として扱う。

### Phase 6: 結果・精算・反省

- 着順と購入券面ごとの払戻を保存する。
- 実購入額を基準に総投資、総払戻、収支、回収率を算出する。
- 実収支区分だけを集計し、デモ／テストレースを累計・レース別収支・反省傾向から除外する。
- 投資0円では回収率をnullとして扱い、画面では「—」を表示する。
- 複数の反省分類と自由記述を保存する。
- 期間、競馬場、券種、買い／見送り別に集計できるようにする。

### Phase 7: インポート／エクスポートとルール

- ---RACE---形式を解析するパーサーと出力フォーマッターを実装する。
- 形式バージョン、必須項目、行番号付きエラー、重複候補を検証する。
- プレビュー後に確認済みデータだけをトランザクションで保存する。
- ルールを不変のバージョンとして管理し、レースから使用版を参照する。
- パースと再出力の往復テストを追加する。

### Phase 8: クラウド配備

- 本番環境へNEXT_PUBLIC_SUPABASE_URLとNEXT_PUBLIC_SUPABASE_ANON_KEYを登録する。
- service role keyを使う場合はサーバー側シークレットとしてのみ登録する。
- HTTPS配信を確認する。Service WorkerとPWAインストールにはlocalhost以外ではHTTPSが必要。
- Supabase AuthのSite URLとRedirect URLを本番ドメインへ合わせる。
- デプロイ後にRLS、ログイン、保存、ロック、精算、再読み込み後の復元を実データなしで確認する。

## 4. 完了前の検証手順

次の順序で実行し、失敗した工程を修正してから先へ進む。

    npm install
    npm run typecheck
    npm run lint
    npm test
    npm run build
    npm start

ローカルプレビュー起動後は、ブラウザ開発者ツールで少なくとも390 × 844pxに設定し、次を確認する。

- 横スクロールが発生しない。
- 下部ナビゲーションと主要ボタンがsafe-areaに隠れない。
- 入力欄が画面拡大なしで操作できる。
- 買い目追加、金額入力、ロック確認が片手で完了できる。
- 予想案と実購入の合計が明確に区別される。
- Manifestが読み込まれ、192px／512pxアイコンが認識される。
- 本番プレビューでService Workerが登録される。
- 初回オンライン表示後のオフライン再読み込みでアプリシェルが開き、端末保存データを復元できる。
- API／Supabase応答や秘密情報がCache Storageへ入っていない。

## 5. テスト範囲

- 単体: 買い目展開、重複除去、点数、金額、収支、回収率、---RACE---パーサー。
- コンポーネント: 必須入力、保存状態、ロック状態、見送り、投資0円表示。
- DB: 制約、RLS、他ユーザー分離、ロック済み更新拒否、履歴追記。
- 結合: レース作成から予想、ロック、実購入、結果、反省まで。
- PWA: マニフェスト、Service Worker更新、静的資産キャッシュ、オフライン案内。
- レスポンシブ: 360px、390px、430px、768px、デスクトップ幅。

## 6. オフラインデータの扱い

PWAのCache Storageは公開アプリシェルと静的資産だけを保持し、API応答やSupabaseのユーザーデータを保存しない。レース、実購入、結果、変更履歴、ルールの作業コピーはlocalStorageへ自動保存する。Supabase接続時はPostgreSQLを端末間共有の正本とし、ログイン後の編集をデバウンスして自動送信する。

通信断中の変更は端末へ残るが、Service Workerによるバックグラウンド同期や自動競合解決は行わない。再接続後は設定画面の全件同期、または対象データの再編集でクラウド保存を再試行する。予想ロックはUIの現在時刻判定に加え、Supabase保存時にもDBトリガーで強制する。

## 7. 明示的な非対応

- 自動投票
- 投票サイトの資格情報保存
- 投票サイトへの購入送信
- 払戻金の自動受取
- 外部サービス規約を回避するスクレイピング
